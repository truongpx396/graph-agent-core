# Cost governance: what the agent spends, and how it stays within limits

The patterns behind the agent's own usage meter and spend limits: pricing a model call, one immutable usage event per call, the dollar caps that sum those events, the holds that keep concurrent turns honest, the gateway backstop, and the history of retiring the old per-turn ledger. They were written in [GRAPH_PATTERNS.md](GRAPH_PATTERNS.md) and moved here, and **keep their original numbers** so every earlier reference ("pattern 58") resolves. The number sequence is shared with that file: 74 is also a graph pattern there (strict tool schemas), so cite this one as `COST_GOVERNANCE.md 74`.

Not here: the billing half of the meter (rating a call in credits, the wallet, the export outbox, reconciliation) is the billing package's, in [`packages/billing/docs/PATTERNS.md`](../packages/billing/docs/PATTERNS.md); what the app hands it is in [BILLING_INTEGRATION.md](BILLING_INTEGRATION.md). The per-turn and token ceilings that end a run early are graph patterns (10, 34, 35). Operating it (sweeps, reconciliation) is in [`deploy/README.md`](../deploy/README.md).

## Patterns

### 26. Usage and cost ledger
**Superseded by 58 and 62-64:** the caps now sum the usage events, nothing writes `usage_ledger`, and its module is gone. What survives from it is how cost is priced and how the limits work.
- **Cost comes from LiteLLM, not a code table.** `app/agent/cost/pricing.py` prices each call from `GET /model/info` (input, output and cached-input rates) and accumulates `State.total_cost_usd`. A two-entry table had priced every other alias at $0 with no signal, blinding every dollar ceiling at once. A self-hosted model is priced by `model_info` in the LiteLLM config.
- **Unknown is not free.** LiteLLM's known $0 (Ollama) is a price; a missing one is `None`, counted per call (`agent_unpriced_usage_total`, alert `ModelUsageUnpriced`) and refused under `UNPRICED_MODEL_POLICY=block`. An alias served by several deployments is priced at the dearest. `block` covers a delegated run too: `run_subagent` refuses a specialist whose own `model:` is unpriced.
- **Degrade paths are counted, and two are alerted** (`agent_cost_governance_degraded_total{path}`): the ones that hide committed spend page (`UsageEventWriteFailing`, which replaced `LedgerWriteFailing`, and `TenantAllowanceUnenforced`, a daily cap that failed open).
- **Resume re-checks the allowance; crash-continue takes a hold.** Approving paused turns once let an over-budget tenant keep spending (the wait is unbounded). `astream_events_resume` refuses an over-budget tenant (`tenant_budget_exceeded`; the thread stays paused; `cancel_run` is never gated) and holds a reservation. The unattended decline loop is a step of an admitted request and is not re-checked. `astream_events_continue_turn` is not refused (it retries admitted work and refusing could strand a turn that already wrote) but takes a hold; the overshoot is bounded by one `MAX_COST_USD_PER_TURN`.
- **The failure mode of the allowance is a decision, in its own module** (`app/agent/cost/budgets.py`, `check_tenant_daily` returns an `Allowance`). When the read fails, `BUDGET_CHECK_FAILURE_POLICY=open` (default) serves the turn, counted and alerted; `closed` refuses it as `budget_check_unavailable`.
- **Four limits, two scopes, two windows.** A limit is `(scope, window, dollars)`: scope `tenant` or `principal`, window `day` (rolling 24 h) or `month` (the CALENDAR month in UTC). Only tenant/day is on by default; `MAX_COST_USD_PER_TENANT_PER_MONTH` and `MAX_COST_USD_PER_PRINCIPAL_PER_DAY`/`_PER_MONTH` are off at 0. The first exceeded limit refuses (tenant before person) and only it is counted (`agent_budget_exceeded_total{scope,window}`); a person over their own limit gets `personal_budget_exceeded`. Crossing 70/85/95% is counted once per window, and only tenant-scope 95% pages (`TenantBudgetNearLimit`).
- **Operators can override a limit per tenant or per person** (`budget_policies`, `postgres-init/18-budget-policies.sql`): keyed `(tenant, subject, period)` with subject `''` (the tenant's own), `'*'` (every person: a plan tier) or one principal; person beats `*` beats the default. **NULL means explicitly no cap and 0 means refuse everything** (the suspend switch). Edited only through `make budget-policy` (audited with `--by`) and cached `BUDGET_POLICY_REFRESH_SECONDS` (30), so **a change, a suspend included, reaches a running worker within that long, not instantly**. A missing table reads as no overrides with one warning. `GET /usage` returns `budgets` with spent, remaining and `resets_at`.
- **The gateway is the backstop** (`app/core/gateway.py`). App-level limits can all be wrong at once (a bug, a loop), so LiteLLM holds a scoped key with its own `max_budget`, minted by `scripts/tools/litellm_key.py`; the master key cannot carry a budget, and sending it would hand over gateway admin with one compromised container. Compose sends `LITELLM_APP_KEY`. The scoped key must still read `/model/info`, or every model would read as unpriced. Every call carries `user` and `metadata.tags` = `tenant:<name>`.
  - LiteLLM's stop is recognised by its error `type` (`budget_exceeded`), not its status (400 on older code, **429 on `main-stable`**). It becomes `provider_budget_exceeded` and the critical `GatewayBudgetExceeded` alert, and `AGENT_RETRY_POLICY` refuses to retry it (it was retried three times, nine gateway requests).
- **Every chat call is metered** (`metering.metered_invoke`, 51), so follow-ups and compaction count. **Still open:** embeddings are neither metered nor attributed at the gateway.
- **Bug:** unfinished turns were not recorded, though timed-out turns spend the most. `_record_unfinished_turn` reads the last checkpoint on the timeout, error and cancel paths.
- **The daily cap counts in-flight turns.** `reserve_budget` records a hold of `MAX_COST_USD_PER_TURN` per running turn (`tenant_budget_holds`), released by id; holds older than `RESERVATION_STALE_AFTER_MINUTES` (5, a constant) stop counting. Without holds, N concurrent turns all read the same "spent so far".
- **Bug:** the first design was one running total per tenant, so a killed worker's amount never aged out and refused real turns over spend that never happened (one timestamp cannot mean both "last touched" and "how old is what this holds"). `test_budget_holds_real_postgres.py` ages real rows, which fake cursors cannot.
- **Gaps:** holds are per tenant, so a person's limit can be overshot by (concurrent turns) x `MAX_COST_USD_PER_TURN`; a monthly window reads a month of rows before every turn, linear in volume (16.6 ms for 300,000 rows; see 58); tokens from a call cut off mid-flight and turns paused and never resumed are not counted; a LiteLLM fallback can serve a call at another deployment's price without saying so; cache-WRITE tokens are billed at the input rate because `langchain-openai` drops that field; a failed reserve means unprotected, not blocked.

### 51. Per-call usage events behind one metering choke point
`usage_ledger` was one row per turn with no key that names a call: enough for a cap, not for billing (a replayed write is unrecognisable, and a provider that deduplicates by a caller-supplied id has nothing to be handed). `usage_events` (`postgres-init/19-usage-events.sql`) is one append-only row per model call, and `metering.metered_invoke` is the one place a chat-model call is made, priced and recorded (specs/010).
- **Identity is verified, not assumed:** `event_id = uuid5(tenant | AIMessage.id)`. The id is langchain's `run-<run id>-<index>`, unique per invocation and identical after a checkpoint round trip; the provider's `chatcmpl-...` id is deliberately not used. `test_usage_events.py` pins it, so a library upgrade that changes id assignment fails loudly.
- **Duplicates are the primary key** (`INSERT ... ON CONFLICT DO NOTHING`; 20 concurrent writers of one event make one row). The table is append-only by trigger (DELETE only when the retention job says so inside its own transaction). `cost_usd` is **NULL when the model has no price**, never 0 (a 0 would be billed as free), and money is `NUMERIC(18,12)` because six places would store a $0.0000004 call as zero.
- **A choke point, because a call site that must remember to meter will forget:** `test_metering_choke_point.py` reads the AST and fails on any new unmetered `llm.ainvoke` and on a stale exemption (the list is empty).
- **Fails open, counted, alerted:** a failed write never fails a turn, but a lost event is lost revenue, so `UsageEventWriteFailing` pages and an unapplied migration is `UsageEventTableMissing`. There is **no kill switch** (58). The write costs p50 0.56 ms.
- **Counted exactly once:** across an answer, a compaction and follow-ups the events' cost equals the turn's running total plus the others' own cost. **Compaction deliberately does not add to the turn's cost budget:** it can summarise tens of thousands of tokens, and charging that to the turn could stop the answer the turn exists to give.
- **An escalated turn is priced as the alias that served it** (GRAPH_PATTERNS.md 68): the routed alias is both `model=` and `model_alias`, and if the call never reaches a model it is repeated on the local alias and recorded as local, which is why the degrade is in the app and not a LiteLLM `fallbacks` entry. An unpriced strong alias keeps the route local whatever `UNPRICED_MODEL_POLICY` says.
- **Gaps:** a response that arrives while the process dies before the event commits is not recorded (the reconciliation against the gateway log is the detector); embeddings are not routed yet (they need the tenant plumbed through nine call sites).

### 57. Carrying the ledger's history into the events, and a first version that could never finish
The caps were about to sum `usage_events`, which only begin when `postgres-init/19` is applied, so switching the read alone would make a monthly cap forget the month so far. This is the additive half, merged first: it changes no behaviour.
- **What it copies:** `make usage-events-carry-over` (`scripts/tools/usage_events_carry_over.py`) copies each ledger row older than the **first real event** as one `ledger:<id>` row. Nothing newer (every turn since was written to both tables, so copying would double a tenant's spend). The cutoff is the first row whose id does not start with `ledger:`, so a carried row never moves it (a naive `MIN` would slide back and stop the second run carrying the rest).
- **History is not a call:** a carried row is never rated, charged or queued for export (a real-Postgres test pins no credits, wallet transaction or outbox row).
- **Bug:** the first version could never finish a large ledger: each run scanned from id 0 and re-read the same carried rows. It now selects only rows not yet carried; a test running three ceiling-limited runs expecting 2, 2, 1 fails on the old query.
- `--tenant` exists because the cutoff is one instant for the whole table and the integration container is shared by every xdist worker, and so an operator can check one tenant first. A test that writes history can break an unrelated test that deletes it, so the carry-over tests clean up and share the retention tests' xdist group.
- **Gaps:** nothing alerts that the carry-over was skipped (`ARGS=--dry-run` printing `Would carry 0` is the check); a turn that straddles the cutoff is counted by its events only; a ledger row from a stretch when events were not written *after* the first one sits past the cutoff and is not carried (`make credit-reconcile` names such a tenant-day).

### 58. The dollar caps sum the per-call events, and the history is carried across instead of forgotten
The caps and `GET /usage` summed `usage_ledger` while billing, the wallet and the export were built on `usage_events`: two records of one spend, kept in step by a test. `app/agent/cost/spend.py::usage_summary` now sums the events, so what is capped, charged, exported and reconciled is one set of rows.
- **Three gaps close by construction:** a turn is counted as it spends, not when it ends; every kind of call is counted; and the cap and the bill cannot disagree.
- **The kill switch had to go:** `USAGE_EVENTS_ENABLED=false` would make every cap read $0 and stop enforcing without a sound, so it is refused at startup. The setting is kept because Settings ignores unknown variables, and an operator's old `=false` would otherwise be dropped silently while they believed writes were off.
- **Deliberate differences from the ledger sum:** an unpriced call adds tokens and $0; the window is `occurred_at`, the time of the call; a running turn is counted twice in the safe direction (its finished calls are events while its hold stands), so a sibling's check can refuse a little early and never let a burst through.
- **Measured, and an index decided against:** with 2,000,000 events in 30 days: tenant rolling 24 h (the always-on cap) 9.3 ms, one person 24 h 5.8 ms, one person month 98 ms, **tenant month 426 ms (a sequential scan)**. A `(tenant, principal, occurred_at)` index would cost 118 MB (32% of the table) and a write per model call to save ~5 ms on an opt-in cap.
- **A scratch script shares the test harness's container:** `ensure_postgres()` caches its container, so a measurement left 2.6M rows and an index that failed an unrelated planner test. Measure on a container of your own.
- **Gaps:** the monthly caps are linear in a month's model calls (off by default; the lever is a per-day rollup written in the event's transaction, not built); a deployment that never applied `19-usage-events.sql` now has caps that fail open (`TenantAllowanceUnenforced` pages).

### 62. The per-turn ledger stops being written: one record of spend, and what that costs
The caps sum the usage events and the reconciliation no longer compares the ledger, so the per-turn `usage_ledger` row had no reader left. Writing it stopped (the turn-end row, the subagent row, `record_usage`, `LedgerWriteFailing` and the `ledger_write` metric path); one record of spend remains, written where the call is made.
- **What it closes:** a turn that timed out, errored, was cancelled or sat paused never reached its end-of-turn write, a MONEY problem because the row was written at the end. Each call's event is now written the moment the call returns.
- **What it costs, plainly:** there is no way back (a release that reads the ledger would see spend only up to the day this deployed), a failing event write is now the only thing that makes a cap under-count (`UsageEventWriteFailing` is its page), and there is no second local record: a lost event is found only by the gateway comparison.
- The unfinished-turn checkpoint re-read stays (it also feeds `agent_tokens_total`), bounded to 2 s. 7 mutants, all caught.

### 63. The usage events get the retention sweep, and it refuses to hide unfinished exports
`usage_events` grows with every model call. `make usage-events-sweep` (`app/agent/cost/usage_events_retention.py`) deletes events older than `USAGE_EVENT_RETENTION_DAYS` (400 by default).
- **A floor, enforced twice:** a monthly cap reads back 31 days and the reconciliation up to 35, so the setting refuses to load below 35 and `sweep_old_events` raises below it BEFORE touching a row.
- **It will not delete evidence of unfinished work.** An event whose export is `pending`, `failed` or `expired` is usage meant to reach a provider and did not; it is kept and counted (`held_back`). Only a `sent` export is finished, and that event goes with its outbox row in ONE statement because of the foreign key. *(Since spec 013 the outbox and this guard belong to the billing package's own sweep over its own `billing_usage_events`: `packages/billing/docs/PATTERNS.md` B3; the agent's sweep records why the guard exists.)*
- **The delete is permitted per transaction, not per session:** the table refuses DELETE unless `usage_events.allow_delete` is on, which the sweep sets LOCAL to its transaction, so it cannot be left switched on.
- **It does not touch the wallet:** a debit keeps its `usage_event_id` as lineage, so keep events at least as long as you may need to explain a charge.
- **Gaps:** nothing schedules it (on purpose: this is the table spend is read from); a `failed` or `expired` export keeps its event until a person resolves it, and there is no "resolved" state; the all-time `/usage` total is bounded by the retention window.

### 64. The budget holds move out of the retired ledger module, and the module goes with its sweep and its setting
The last live thing in the old ledger module was the in-flight budget holds. They are now `app/agent/cost/budget_holds.py`, moved verbatim, and the module, its sweep script, `make usage-ledger-sweep` and `USAGE_LEDGER_RETENTION_DAYS` are deleted. The `usage_ledger` TABLE stays, frozen and read-only, because the carry-over copies from it; dropping it is a later, destructive decision.
- `test_the_ledger_module_is_gone_so_a_stale_caller_fails_loudly` asserts the old import raises `ModuleNotFoundError`.
- **Two collisions only a shared database shows:** an outbox foreign key refused a carry-over test's delete of every real event (it clears the outbox first, in the same transaction), and the carry-over race test's 3,000 old events hit the retention test's 2,000-row ceiling before its own rows (it passes an explicit `max_batches` and each fixture purges what it wrote). The shared xdist group stays, renamed `usage_events_old_rows`.
- **Gaps:** the `usage_ledger` table and its indexes (`postgres-init/03`, `17`) remain on every volume, and `12-tenant-budget-reservations.sql` still has a historical comment naming `record_usage`.

### 74. What the gateway sees of spend: priced local models, a readable per-person end user with a default cap, the conversation on every call, and a pinned image
Four changes to the same seam: a gateway cap is only as good as the price and the identity behind it.
- **A local model is priced, or no gateway budget can trip on it.** `/model/info` reported local aliases at a known 0 (and `vision` as `null`), and LiteLLM skips budget checks for a model whose two prices are both 0. Every alias in `litellm-config.yaml` now states a shadow price in `model_info` (the order of magnitude hosted providers charge for open-weights models of that size, not a bill), each alias stating its own because a deployment with no price *inherits* another deployment's for the same underlying model (a test requires one price per underlying model). Billing now debits a few millionths of a credit for local usage where it debited none.
- **Three chat tiers, two waiting for a hosted model:** `chat`, `chat-medium` and `chat-strong` (specs/014): always present, keyless local stand-ins in dev, three `LLM_MEDIUM_*` variables defaulting to `chat`'s in production, and no gateway fallback naming them (it would answer with one model and price the call as another). Attaching Gemini is one dev entry or three prod variables. **Not verified, no key yet:** Google documents tool calling and streaming on its OpenAI-compatible endpoint but not `stream_options.include_usage`, which the app needs to meter a streamed call. `litellm_key.py create` now follows the prod config's aliases (it listed only `chat,embed`).
- **The end user is the person, readable, and the default gateway budget caps each person (for chat).** The app sends `user` = `tenant:<tenant>/user:<principal>`, each part percent-encoded (`gateway.parse_end_user_id` reads it back strictly, so another application's end user on a shared gateway is not mistaken for ours). LiteLLM keeps it as the end user, so its Customer Usage view filters by person. `max_end_user_budget_id: person-default` in both configs names the budget every end user without one inherits; `litellm_key.py person-budget set --max-budget <usd> [--budget-duration 30d]` creates it and `info` reads it back (exit 1 when missing). **There is no tenant-wide cap at the gateway** (the app's own tenant limits are exact and stay), and it **fails open**: a name with no object behind it makes LiteLLM apply nothing, hence the `info` step in the runbook. It is a backstop above the app's limits, not a copy, and the call that crosses the line still goes through.
- **Why it was a hash and why it can be readable now:** a person's name has no business reaching a model provider, so the first version hashed it. `make gateway-check` (`scripts/checks/gateway_check.py`) now runs the PINNED image on the shipped dev config with a stub backend and shows nothing identifying (end user, tenant, principal, conversation or metadata) reaches the backend on the Ollama route or an OpenAI-compatible one, and that every alias is priced. A bump re-runs it. The reconciliation reads the tenant off the end user and sums its people into its day; spend-log rows under the older hashed id are still attributed (`gateway.legacy_end_user_id`), a branch that can go once the gateway holds none.
- **The conversation is on every call:** `litellm_session_id` and `metadata.session_id` carry the `thread_id`, which the app's Langfuse trace already uses, so the proxy's traces and the app's turn land in one session (the cron scripts pass a synthetic id, so each digest day and follow-up draft is a session too). That the Langfuse trace is filed under it was read from source, not seen in the UI.
- **The gateway image is pinned by digest in both compose files** (the same one, a test): the multi-architecture index of `main-stable` (LiteLLM 1.94.1). The tag moved under this app once (the budget stop went 400 to 429) and a LiteLLM release on PyPI was compromised in March 2026. A bump is deliberate: `deploy/README.md`, "Bumping the LiteLLM image".
- **The containerized app could not carry the scoped key:** a container does not read `.env`, and the dev `x-app-env` block had no `OPENAI_API_KEY`, so every containerized role sent the dev MASTER key and the scoped key's budget never moved. The block now carries `OPENAI_API_KEY: ${LITELLM_APP_KEY:-sk-anything}`. **Gap:** one key has two names (`OPENAI_API_KEY` for a host process, `LITELLM_APP_KEY` for a container); unifying them means teaching `Settings` a second name.
- **A gateway-side router alias is unpriced, not free:** LiteLLM's own routers (`auto_router/...`) report input and output 0, which `pricing._rate` accepts as an honest price, so every call would be metered at $0 while the gateway priced the real model. `pricing._is_gateway_router` makes such an alias unknown, so it is counted (`ModelUsageUnpriced`) and refused under `block`. The app routes in `route_model` instead (GRAPH_PATTERNS.md 68). **Gap:** a router kind under another name would read as 0 again, and the exact cost is in a response header `ChatOpenAI` does not surface.
- **Decided against:** an alert on LiteLLM's `litellm_zero_cost_requests_total` (production Prometheus does not scrape LiteLLM, and `ModelUsageUnpriced` counts the same calls).
- **Not run:** budget enforcement against a live gateway with its database (read from the installed LiteLLM: `_check_end_user_budget` refuses when `spend > max_budget`), and the CI tiers.
- **Gaps:** embeddings carry no end user, so no per-person gateway cap covers them; an unpriced model is invisible to every gateway budget; the window is LiteLLM's own (a `30d` budget resets at the next month boundary), not the app's rolling day or calendar month; a readable end user is only as private as LiteLLM's not forwarding it, which `make gateway-check` verifies for the pinned image and nothing verifies for a future one; the digest has no automated bump (Dependabot here is `github-actions` only); one customer row per person accumulates in LiteLLM's database.
